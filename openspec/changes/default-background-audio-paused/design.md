## Context

全局 `BackgroundAudioProvider` 已经是唯一的音频状态源，并且只在偏好为 `playing` 时于挂载后请求播放。问题集中在偏好解析：空值和未知值目前被宽松地解释为播放，导致首次打开应用可能有声启动。

## Goals / Non-Goals

**Goals:**

- 让无保存偏好的首次打开保持暂停。
- 让已保存的播放意图继续恢复播放。
- 保留旧版本 `on` / `off` 存储值的兼容性。
- 让测试明确证明默认状态不会调用音频播放。

**Non-Goals:**

- 不修改播放器、两首歌的歌单、循环切歌或 UI 布局。
- 不增加故事栏独立音乐；故事栏继续复用全局控制器。
- 不改变用户点击播放、暂停、切歌或业务路由行为。

## Decisions

### 1. 采用白名单解析播放意图

`readBackgroundAudioPreference` 仅把 `playing` 和历史值 `on` 解释为播放；`paused`、`off`、空值及未知值统一解释为暂停。这样默认值安全且不会把损坏的本地存储误判为自动播放许可。

备选方案是仅把空值改为暂停、未知值仍播放，但这会让无效存储继续产生意外声音，没有必要保留这种宽松分支。

### 2. 复用现有 Provider 启动边界

不新增启动状态或故事栏播放器。Provider 已经根据 snapshot 的 `preference` 决定是否调用 `requestPlayback`；默认偏好改为暂停后，首次挂载自然跳过播放请求，而显式 `playing` 仍沿用原路径。

## Risks / Trade-offs

- 用户若曾保存旧值 `on`，刷新后仍会播放；这是兼容已表达播放意图的必要行为。
- 用户若本地存储中存在未知值，将从本次启动起静音；用户可通过音乐按钮主动恢复播放。

## Migration Plan

1. 修改偏好解析、测试和 baseline spec。
2. 保持现有 localStorage key 不变，无需迁移脚本。
3. 运行背景音乐专项测试、类型检查和构建。

回滚时只需恢复默认解析为播放，不涉及数据或资源迁移。
