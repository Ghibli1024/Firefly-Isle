## 背景

Firefly-Isle 已经把实验室指标建模为 `PatientRecord.labResults`，并持久化到 `lab_results`。但当前用户能看到的只是 `/record/:id` 里的基础表格。侧栏 `统计` 仍是敬请期待，所以用户无法把血常规、血生化、肿瘤标志物当作主流程来浏览和监测。

用户现有的本地 `update-followup-data` skill 已经证明了正确的领域形状：固定实验室指标字典、按日期沉淀长期读数、参考范围、血常规派生指标、可绘图序列、最近异常扫描、肿瘤标志物趋势监测。产品方向不是继续把结果放在本地 Excel，而是把最终表格和图表放进网页端。

## 目标 / 非目标

**目标：**

- 让 `统计 / 实验室趋势` 成为真实网页路由，并消费 Supabase 里的实验室数据。
- 支持在 `/app` 输入区上传实验室报告、OCR 文本确认、结构化提取和保存。
- 支持 `/analytics/demo`，当没有真实输入时提供与 `/record/demo` 类似的演示统计页。
- 增加批次级数据模型，让一次上传报告 / 一次检查可以拥有多条实验室读数。
- 继续以 `lab_results` 作为图表和监测计算的唯一读数事实源。
- 把 `update-followup-data` 的关键能力产品化：指标字典、分类映射、参考范围解析、NLR / PLR / MLR 派生、监测规则。
- 按 `血常规`、`血生化`、`肿瘤标志物` 分组浏览。
- 为选中指标提供网页端折线图和等价数据表。
- 汇总最近异常指标，以及连续两次上涨超过 20% 的肿瘤标志物。
- 所有临床信号保持非诊断语气。

**非目标：**

- P0 不要求本地 Excel 文件参与使用。
- 统计页不承载文件上传表单；上传归 `/app` 输入区。
- 浏览器不读取 `/Users/Totoro/.../血常规.xlsx` 或其他 iCloud 本地工作簿路径。
- 不提供 AI 诊断、疾病进展判断、用药或治疗建议。
- 不做跨患者队列统计。
- 不做完整 BI dashboard 或泛化数据分析产品。
- P0 不自动迁移历史 Excel 数据；历史导入可以作为后续能力。

## 设计决策

### 决策 1：网页端拥有最终表格和图表体验

统计页在 React 里渲染趋势表格、折线图、异常汇总和监测提醒。本地 Excel 只保留为历史工作流参考，不作为运行时依赖。真实数据页为 `/analytics/:id`，无输入演示页为 `/analytics/demo`。

备选方案：

- **继续让 Excel 承载图表：**不采用。它不符合用户想要的网页端体验，也把核心价值留在 Firefly-Isle 之外。
- **让浏览器直接读取本地 iCloud Excel：**不采用。普通网页应用无法稳定持续访问任意本地路径，也会带来脆弱的权限和隐私行为。

### 决策 2：新增 `lab_report_batches`，继续让 `lab_results` 作为读数真相源

Supabase 需要把“一次上传 / 一次检查事件”和“该检查里的单项读数”拆开：

- `lab_report_batches`：记录一次上传报告，包括分类、检查日期、OCR / 复核状态、源文件元数据、可选 OCR 文本。
- `lab_results`：记录一个指标读数，可选关联到某个批次，包含指标编码、名称、数值、单位、参考范围、来源、派生元数据。

这样可以避免把报告级信息塞进每一条读数，同时保留从 `lab_results` 查询趋势的简单性。

备选方案：

- **只扩展 `lab_results`：**更简单，但缺少干净的位置保存源文件、OCR 状态和报告级复核信息。
- **每个实验室分类一张表：**不采用。分类是数据，不是 schema；拆表会重复查询和 RLS 逻辑。
- **P0 做数据库指标字典表：**暂缓。已知映射用 TypeScript 静态字典足够，测试也更直接。如果未来用户需要自定义范围，再迁移到 Supabase 字典表。

### 决策 3：实验室字典是应用逻辑，不藏在 prompt 里

网页摄入流程必须使用显式字典，并参考 skill 里的映射：

- `blood-routine`：血常规项目，加上派生 `NLR`、`PLR`、`MLR`。
- `blood-biochemistry`：血生化项目和参考范围。
- `tumor-marker`：CEA、CA125、CA15-3、CA19-9、CA50、CA72-4。

OCR / LLM 可以辅助提取，但保存前必须把结果归一化到这些字典。

### 决策 4：监测结论计算出来，不持久化

最近异常汇总、折线图序列、肿瘤标志物上涨提醒，都从 `lab_results` 即时计算或通过纯函数计算。它们不应该作为单独事实存到数据库，否则会和原始读数漂移。

### 决策 5：最近异常按分类计算

血常规、血生化、肿瘤标志物不一定同一天检查。最近异常汇总应使用“每个分类自己的最近检查日期”，而不是一个全局最近日期；否则会漏掉某个分类真正最新的结果。

### 决策 6：肿瘤标志物连续上涨需要三个有效点

一个肿瘤标志物需要有三个按时间排序的有效读数，形成相邻两段上涨，并且两段涨幅都大于 20%，才触发提醒。缺失、零值或非正前值不参与百分比涨幅判断。

### 决策 7：视觉基准跟随选中的深色控制塔图，上传入口回到 /app

实现时以选中图作为布局意图，但要翻译成真实 V3 token 和可访问组件：

- 侧栏 `统计` 激活态。
- 页头标题 `统计 / 实验室趋势`。
- 三个顶部摘要：最近异常、肿瘤标志物连续攀升、覆盖指标。
- 左侧分类 tabs 和指标列表。
- 右侧折线图和等价数据表。
- 底部异常表和肿瘤标志物上涨提醒。
- 底部非诊断提示。
- 不在统计页放上传表单；统计页空态指向 `/app` 输入区和 `/analytics/demo`。

## 风险 / 取舍

- **风险：OCR 对中文指标名映射不稳定** -> 缓解：使用显式字典归一化，并要求保存前进入确认表格。
- **风险：同一个患者、分类、日期重复上传** -> 缓解：按患者、分类、检查日期检测已有批次，并要求用户确认替换或取消。
- **风险：低基线肿瘤指标产生百分比噪音** -> 缓解：忽略非正前值，文案保持“趋势提醒”；最小绝对增量可作为后续问题。
- **风险：只有图表会影响可访问性** -> 缓解：每个图表都必须有等价数据表和文字状态标签。
- **风险：Supabase 迁移影响已有 `lab_results` 调用** -> 缓解：新增列使用 nullable / default，保持现有行映射兼容。
- **风险：页面变成泛化 dashboard** -> 缓解：严格以选中的临床控制塔图和 V3 设计系统为实现基准。

## 迁移计划

1. 增加向后兼容的 Supabase schema 变更，保证已有 `lab_results` 仍可读取。
2. 增加实验室字典、归一化和趋势纯逻辑，并配套测试。
3. 增加 `/app` 文件输入、实验室报告摄入 UI 和持久化流程。
4. 增加 `/analytics/:id`、`/analytics/demo` 路由和侧栏导航。
5. 从已有和新保存的 `lab_results` 渲染统计页。
6. 用单元测试、路由 / 组件测试、Supabase 迁移测试、`openspec validate --all` 和聚焦应用测试验证。

回滚策略：如果统计页出现问题，可以先从侧栏隐藏该路由，同时保留现有 `/record/:id` 实验室趋势。因为新增 schema 是增量式，且 `lab_report_batches` 独立存在，已有患者记录和实验室读数仍然可读。
